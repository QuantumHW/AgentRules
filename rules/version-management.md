# 根据兼容性与发布单元管理版本

## 适用场景

项目已有版本化产品或明确的版本维护要求，且任务涉及版本判断、版本字段或发布准备。产品可以是软件、规则库、Skill、提示词或文档资源包；不以仓库含有代码为前提。普通文稿没有版本约定时不自动建立版本体系。

## 行为约束

### 确认策略与基线

- 先查项目的版本策略、权威版本字段、发布单元、已确认的发布基线与当前差异；存在 Git 时核对正确仓库的状态、HEAD、相关历史和已有发布依据，交付前复核，不能沿用上一轮状态或把最新提交等同于最近发布。
- 既有策略可以采用 SemVer、日期版本或平台规则，不擅自转换。需要建立新策略时，优先建议 SemVer，并先明确兼容性承诺的对外契约；对应用或工具，可包括项目承诺稳定的命令、配置、数据格式与行为，不仅是函数签名。
- 对以规则、Skill 或文档资源为产品的项目，按实际提供的行为能力、适用场景、生成流程、入口和资源引用判断变化；规则正文变更可能就是功能变更，不能套用“只有源码修改才更新版本”的前提。具体承诺及递增授权仍取自目标项目。
- 项目声称采用 SemVer，但既有递增方式与其兼容性语义不一致时，指出具体矛盾并建议调整；不能把偏离标准的惯例仍描述为符合 SemVer。

### 采用 SemVer 时

- 正常版本使用 `MAJOR.MINOR.PATCH`，各数字不含多余前导零。对于 `MAJOR >= 1` 的稳定版本，按相对于发布基线的整体兼容性判断：不兼容的对外契约变化递增 MAJOR；向后兼容的新功能或公开弃用递增 MINOR；仅向后兼容的缺陷修复递增 PATCH。递增高位时低位归零。
- 不按代码行数、功能“大小”、对话轮次或提交次数决定版本位；很小的破坏性改动也不能伪装成 PATCH。同一发布单元包含多类变化时采用其中要求最高的级别。
- `0.y.z` 属于初始开发阶段，按项目明确的稳定性与发布约定处理，不机械套用稳定版本规则，也不擅自宣称已经稳定。
- 同一个尚未发布的目标版本可包含多次修改或提交，不因每次提交而累加版本。新增变化提高了所需级别时重新评估目标，不能把“工作区未提交”当作维持较低级别的理由。
- 已发布版本的内容保持不可变；后续修正使用新的版本，不通过覆盖发布包或重指已有发布标签来维持原版本。预发布标识、构建元数据与平台构建号分别按既有约定管理，不冒充正式发布；构建元数据不影响 SemVer 优先级。

### 执行与同步

- 仅改辅助说明、注释、排版或其他不影响产品行为和契约的内容时，不默认递增产品版本；若项目的发布政策要求为此发布新包，按该政策处理。先区分文档本身是否为产品，不把可执行指令的修正、新规则或新工作流归入辅助说明。这是 AgentRules 的默认工作约束，不是 SemVer 对文档发布的禁令。
- 不仅凭扩展名判断变更性质：配置、资源、声明式规则、脚本或依赖变更同样可能影响产品行为；按实际影响评估。
- 用户只要求判断或建议时，不写版本字段。更新授权可以来自本次请求或项目已确认的持续维护约定；已有授权时不重复要求用户单独批准同类版本同步。按授权同步实际存在的权威版本源及受其约束的包配置、文档和产物元数据；独立版本化组件、历史记录与构建号不要求机械改成相同数值。
- 版本修改不等于授权创建标签、提交、推送或发布。基线、契约或发布状态不明时指出缺口，给出有条件的建议，不编造正式版本或发布事实。

## 推荐行为

从已确认发布的 `1.4.2` 修复兼容性缺陷，建议 `1.4.3`；同批又增加兼容功能，目标改为 `1.5.0`，不因中间提交过一次就改成 `1.5.1`。若同时删除稳定接口，应评估 `2.0.0` 及迁移影响。

规则库修正失效引用且保持现有用法属于兼容修复；新增可复用规则、场景或生成能力属于兼容扩展；移除既有入口或破坏已承诺的生成约定须评估不兼容影响。这些判断与产品文件是否为 Markdown 无关。

## 例外

项目已采用其他版本体系、文档独立发布或多组件独立版本时，保留实际约定。版本变更触发发布流水线或有额外审批要求时遵守该边界；不把建议采用 SemVer 表述为项目已经采用。

## 冲突关系与依据

[factual-integrity](factual-integrity.md) 约束发布基线与验证事实，[scope-control](scope-control.md) 约束写入和发布授权，[change-traceability](change-traceability.md) 处理进度与提交记录。

兼容性、版本格式与发布不可变性的依据为 [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)；发布单元的复核、授权和同步方式是 AgentRules 的工作流程约束，不应冒充标准条文。
