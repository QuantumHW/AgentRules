# 成品只表达当前主线

## 适用场景

创建或修改功能、界面、页面、文件、文档及其他交付物时，约束其正式名称、标题、界面文案和正文；不以是否使用 Git 或是否对外发布为前提。

## 行为约束

- 成品必须直接呈现修改后的当前主线内容，不得把修改过程、已删除内容或与旧版本的差异写进标题、文件名、界面文案或正文。
- 不得使用“无 XX 版本”“去除 XX 后的版本”“不含 XX”“精简版”“修订版”“替代版”等因本次修改而产生的附加标签，除非这些名称本身就是经过明确确认的正式产品分类。
- 用户要求删除某项内容时，直接删除该内容并同步整理相关结构，使剩余内容自然、完整；不得额外声明该内容已被删除，也不得保留解释删除行为的占位文字。
- 文件和页面沿用原有正式名称；只有用户明确要求改名，或已经确认的信息架构需要长期并存的正式分类时，才采用新的名称，不自行为同一成品另建“修改后”副本。
- 修改原因、过程和差异只进入用户要求或项目既有流程规定的进度记录、提交说明、变更日志或交付说明，不混入面向用户的成品。不能为记录变化擅自新增日志或目录。

## 推荐行为

删除“活动安排”中的一节后，标题仍为“活动安排”，直接衔接剩余内容；不要改成“无交流环节版本”，也不要加“原交流环节已删除”。交付前同时核对实际文件名、页面标题、界面字符串和正文。

## 例外

用户明确指定的文件名、已确认的正式产品分类、模板要求的版本标识，以及明确要求的修订对照、迁移指南、历史记录或评审材料，可以表达其必要的版本与差异。此例外不授权在其他成品中附加过程标签。

真实能力限制、失败原因、适用条件和必要风险必须如实说明。“离线模式不支持云端同步”属于能力边界，不能仅因出现否定词就删除。判断依据是表达用途与项目事实，不是关键词禁用。

## 冲突关系

[factual-integrity](factual-integrity.md) 与 [technical-accuracy](technical-accuracy.md) 优先；当前主线表达不等于掩盖限制或宣称未实现能力。[scope-control](scope-control.md) 约束改名、另存与日志创建的授权；[concise-writing](concise-writing.md) 处理信息密度，本规则处理成品与修改过程的边界。
