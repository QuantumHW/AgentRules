# proposal：项目申报书

适用信号：存在申报指南、申请书模板、任务书或申报材料，目标是编写或修订技术研发项目申报书。

## 引用规则

- [core](../rules/core.md)、[factual-integrity](../rules/factual-integrity.md)、[scope-control](../rules/scope-control.md)。
- [concise-writing](../rules/concise-writing.md)、[technical-accuracy](../rules/technical-accuracy.md)。
- [current-deliverable](../rules/current-deliverable.md)；已有阶段或变更记录要求时补选 [change-traceability](../rules/change-traceability.md)。
- 有固定模板或格式文件版面要求时，补选 [template-preservation](../rules/template-preservation.md)；涉及数据建设、研究对照或机制验证时，补选 [research-validation](../rules/research-validation.md)。
- 任务确含系统方案设计且存在扩展冲动时，补选 [anti-overengineering](../rules/anti-overengineering.md)；不引入软件错误处理要求。

## 材料与写作依据

- 在执行环境指令层级内，以用户当前要求确定工作范围，以有效指南、用户确认要求和模板确定申报约束，再用正式材料、指定补充资料及已核验公开来源支撑事实。通用经验不能补造项目条件；用户要求与指南冲突时说明对申报符合性的影响，不静默覆盖。
- 每节先检查当前稿、填写提示、指定补充资料和相关原始来源，核对其他已填写区域。将核实材料用于相关论证，不为体现“已读”而堆砌无关资料。
- 来源核验记录与缺项清单按既有约定放在正文之外；正文按需要使用正式引文或自然注明论文、机构、年份，不叙述查证过程，不裸贴无必要的长 URL，也不删除指南或引用格式要求的链接。
- 区分已具备、正在开展和拟形成；人员职称、单位声望及技术需要不能证明设备、投入、合作、产权或性能事实。关键缺项集中报告，不大量插入“待补充”，不把未知合作写成无合作。

## 正式叙述与归属

- 以申请团队为主体，直接叙述事实、方法和任务，不使用“网页显示”“根据用户提供”等代笔或查证口吻。保留正式引用，不用隐藏来源来营造已有成果。
- 成员相关成果可作为研究基础，但应保留共同成果、依托机构及产权的准确归属；研究队伍写专业能力、经验和互补关系，不拼接个人简历。模板要求的姓名、履历和作者信息仍须保留。
- 通过具体问题、机制、方法差异、任务和验证依据体现技术含量，不以政策堆砌、宣传形容词或无证据的“首创、领先、填补空白”代替论证。已确认承诺不擅自弱化为“力争、可能”，真实不确定性仍准确保留。

## 章节职责与对应关系

按目标模板中实际存在的栏目选择以下要求，不强加固定章节号、分条方式或排列顺序：

| 栏目职责 | 行为约束 |
| --- | --- |
| 项目理解与现状 | 从实际需求、问题及影响说明价值；分析其他团队代表方法的验证范围、局限、趋势和差距，不用名称罗列替代分析，不把自有成果混作外部研究现状。 |
| 目标与指标 | 目标遵守模板的连续叙述或分条要求；指标覆盖已核验指南，新增指标须可测且有实现依据。指南或专项要求未读全时，不宣称覆盖完成。 |
| 研究内容、关键技术与创新 | 内容说明研究对象、问题、机制和产出；关键技术凝练真正难点。按模板分别展开，不能复制段落后换标题；创新按实际差异及验证依据说明，不凑数量。 |
| 技术方案 | 回答如何实现，写清模块输入输出、数据流、调用关系、状态传递、执行验证及必要失败处理；关键技术与解决途径逐项对应，名称、数量、顺序及图文一致。区分已有工具能力与本项目的数据、算法、微调、接口、集成及验证工作。 |
| 基础与条件 | 使用可核验的相关研究、软件和设施材料，说明与本任务的联系，不将计划建设、机构资源或软件能力写成团队已有测试成绩。 |
| 合作 | 核对基本信息及已确认关系；有合作时按依据说明任务、能力、条件与经费，不新增单位、分工或资金承诺。确认无合作后才表述无合作。 |
| 预期成果 | 从前文任务导出具体载体及内容，与基本信息中的数量、类型和口径核对；使用已确认数量，不擅填区间、凑类型或新增知识产权承诺。 |
| 周期与进度 | 保持模板字段，按已确认周期及技术依赖组织里程碑和阶段成果；模板或用户要求按季度时逐季度安排，不擅自固定所有项目的周期、结束措辞或标点。日期未知则留空，不编起止年月。 |

## 执行与交付

- 内部维护“问题—目标—研究内容—关键技术及解决途径—指标与验证—成果—进度”的对应关系；创新点须对应技术和验证，全文名称、数量、条件和口径一致。映射不写入正式正文。
- 核对预算、周期、工作量、人员分工和交付要求。仅修改授权章节及必要关联引用；受保护区域可读取检查，发现一致性冲突在正文外报告，不为闭合对应关系越权改写。
- 按章节推进，核验该节事实、逻辑、模板及适用的版面要求后继续；完成已授权工作，不为常规措辞频繁询问。
- 交付指定工作稿，简述完成范围、关键缺项和实际验证；指南未核验、指标缺失或基本信息一致性未闭合时，不宣称已满足提交条件。

## 组合边界

可与 documentation 组合处理格式，与 academic 组合处理研究证据；单独使用本 Profile 也能按需发现上述专项 Rules。去重后保留申报专属的指南覆盖、指标映射和预算交付约束，不把计划指标写成实测成绩。原项目的章节授权、单位名称、研究任务、数量、周期、图示工具和工作区路径，仅在目标项目明确采用时写入规范。
