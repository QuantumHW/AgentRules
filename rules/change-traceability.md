# 变更记录与交付可追溯性

## 适用场景

项目已有进度、验收、Git 提交或变更日志约定，或用户明确要求这些交付内容。不因项目存在 Git 就自动创建进度文件或发布流程。

## 行为约束

- 按已确认的阶段与验收条件记录真实进展，具体说明完成项、实际验证和未完成项，不以“已优化”“基本完成”替代可核对结果；项目要求任务列表时区分完成与待办状态。
- 维护既有进度历史，更正旧结论时追加更正及依据，不覆盖历史来制造“始终正确”的记录。记录位置及是否纳入 Git 按项目约定，临时测试记录不自动成为公开交付物。
- 交付前核对当前差异及验证范围；构建、测试、运行和真实环境覆盖分别报告，计划与未执行验证不标记为完成。
- 提交说明对应实际可独立审阅的改动，不为无独立意义的中间步骤拆分建议。只有存在实际提交时才引用 commit 或 SHA，不给未提交改动虚构编号。
- 项目采用 Conventional Commits 时使用 `<type>[optional scope][!]: <description>`；新功能用 `feat`、缺陷修复用 `fix`，其他类型按实际改动选择。说明语言沿用项目约定，不将某个项目的中文要求推广到所有项目。
- 采用该规范时，通过 `!` 或 `BREAKING CHANGE:` 标明破坏性变更；破坏性变更可出现在任何类型中，不能因使用 `fix`、`docs` 或 `refactor` 就忽略它。提交类型提供分类依据，版本仍需检查实际兼容性和发布策略。
- Git 操作按实际授权执行；生成提交建议、更新进度或阶段完成不等于授权暂存、提交、推送或配置远程。项目约定用户自行操作时保留该约定，不自行启用自动提交或联网同步。

## 推荐行为

记录“已修改请求校验；相关单测已通过；真实网络路径未验证”，而非“功能全面完成”。若项目要求给出提交建议，说明应覆盖当前差异，而非沿用上次建议。

## 例外

没有相关流程的项目只需准确的交付说明；只读任务不写进度文件。用户明确要求修订历史或操作 Git 时按其具体授权处理，不从来源示例中推断权限。

## 冲突关系与依据

与 [current-deliverable](current-deliverable.md) 分离正式成品与变更过程；与 [version-management](version-management.md) 区分提交与发布单元。

提交语法和破坏性变更标记依据 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。进度格式、语言及 Git 操作权限由项目约定，不是该标准统一规定的内容。
